## 決めたこと(ユーザー、2026年11月18日)

- `legacy/src/`を挙動の基準として扱う。今のコードの挙動がlegacyと違い、根拠が見つからなければ「疑わしい」と判定する。
  - 理由: legacyは動作していた実装で、このプロジェクトはそのリファクタリングとモダナイズとして始まった。
  - 前提: 基準は暫定。違いの量と根拠の強さによっては、レビューの後でlegacyの位置づけを弱める。だから根拠のある違いも数えて残す。
  - legacyの問題の多くはユーザーも自覚していて、作り直しのときに大きく変えるよう指示していた(ユーザーの説明)。指示して変えた違いは、根拠の強さを「指示」として別に数える。
  - `legacy/README.md`の役割の書き直しは、レビューの後に決める。
- 区切りごとに1セッションで進める。
- 区切りのコードは下請け(サブエージェント)に読ませ、指摘は親のセッションがコードを読んで確かめてから載せる。直すかどうかは、ユーザーが一件ずつ決める。レビューのセッションでは直さない。
- 根拠は、作り直しのときの会話記録からも探してよい。このリポジトリは公開なので、理由は自分の言葉で書き、原文を引用しない。記録そのものはリポジトリに入れない。

## 観点

指摘は5種類に分ける。1〜4は下請けにも探させ、5は親が「引き継いだ候補」から確かめる。

1. **不具合**: 具体的な入力・状態と、誤った結果を書けるもの
2. **legacyとの違い**: 挙動の違い(書くレジスタと値、MIDIメッセージへの反応、データの解釈、音の高さ・大きさ・時機)。名前・構造・書き方の違いは、挙動を変えない限り数えない。違いごとに根拠の強さを付ける:
   - **指示**: ユーザー(legacyの設計者)が、作り直しのときに変えるよう指示した
   - **強**: ハードウェアの資料・測定・テストで裏づけられる。またはlegacyの不具合を直したものとして示せる
   - **弱**: 文書・worklog・コミットのメッセージ・会話記録に理由が書かれているが、裏づけは無い
   - **無**: 見つからない。「疑わしい」として扱う
3. **チップファミリー間の不一致**: 同種の処理が、チップによって違う作りになっているもの(`CLAUDE.md`の必須要件)
4. **使われていないコードと、古いままの重複**
5. **決めた仕様との食い違い**: 作り直しのときに決めた仕様と違うのに、コードと文書の辻褄は合っているもの。コードだけでは見えない

## 1セッションの手順

1. HEADを見て`git fetch`する。「進み具合」で次の区切りを選ぶ
2. 会話記録のあるマシンなら、経緯のメモを読み、その区切りに関わる決定を拾っておく
3. 「下請けへの依頼文の型」に区切りのファイル一覧を入れて、下請けに渡す。今のコードとlegacyを合わせて1万行を超える区切りは、2人に分けてよい
4. 下請けの指摘を、親が全部コードで確かめる。根拠が「無」の違いは、親が会話記録でもう一度探す。下請けの行番号はずれていることがある(区切り3では、`FnumUtils.h`・`Fnum.h`を指す番号が実際と違った)ので、載せる番号は親が開いて見たものにする。確かめる途中で見つけたものも載せ、親が見つけたと書く
5. 「引き継いだ候補」のうち、その区切りのものを確かめる
6. 確かめた結果を「指摘の一覧」に書き、「進み具合」を更新する。依頼文の型と書式に直す所があれば、この文書も直す
7. コミットする

## 下請けへの依頼文の型
