## 1セッションの手順

1. HEADを見て`git fetch`する。「進み具合」で次の区切りを選ぶ
2. 経緯のメモのあるマシンなら、それを読み、その区切りに関わる決定を拾っておく
3. 「下請けへの依頼文の型」に区切りのファイル一覧を入れて、下請けに渡す。今のコードとlegacyを合わせて1万行を超える区切りは、2人に分けてよい
4. 下請けの指摘を、親が全部コードで確かめる。根拠が「無」の違いは、親が会話記録でもう一度探す。下請けの行番号はずれていることがある(区切り3では、`FnumUtils.h`・`Fnum.h`を指す番号が実際と違った)ので、載せる番号は親が開いて見たものにする。「使われていない」という報告は、親が呼び出し元をgrepで数え直す(区切り5では、実際には使われている関数が1件混ざっていた)。確かめる途中で見つけたものも載せ、親が見つけたと書く
5. 「引き継いだ候補」のうち、その区切りのものを確かめる
6. 確かめた結果を、指摘の文書に区切りの見出しを作って書き、指摘の文書の「区切りごとの数」と、この文書の「進み具合」を更新する。依頼文の型と書式に直す所があれば、それぞれの文書を直す
7. コミットする

## 下請けへの依頼文の型

`<…>`は親が埋める。会話記録の場所は、記録のあるマシンでだけメモリから入れる。

```text
FITOM_X(C++17)の次のファイルを読んで、レビューしてください。差分ではなく、今あるコードの全体が対象です。
ファイルは書き換えないでください。Bashのcdは使わず、絶対パスかツールのパス引数で読んでください(cdはフックが止めます)。

今のコード: <区切りの「今」の一覧>
対応する旧実装(legacy/src/): <区切りの「legacy」の一覧>
旧実装は動作していた実装で、挙動の基準です。旧実装の問題の多くは、作り直しのときに設計者の指示で意図して変えています。
会話記録: <場所と引き方。記録が無ければこの行を消す>

挙げてほしいもの:
1. 不具合。具体的な入力・状態と、誤った結果を書く
2. 旧実装との挙動の違い。書くレジスタと値、MIDIメッセージへの反応、データの解釈、音の高さ・大きさ・時機の違い。
   名前・構造・書き方の違いは、挙動を変えない限り挙げない。違いごとに根拠を探し、強さを付ける:
   指示 = 設計者が変えるよう指示した(会話記録) / 強 = ハードウェアの資料・テスト・旧実装の不具合の修正として示せる /
   弱 = 文書・worklog・コミットのメッセージ・会話記録に理由があるが、裏づけは無い / 無 = 見つからない
   探す場所: docs/design/・docs/manuals/・docs/interfaces/・docs/worklog/・git log(該当行のgit blameから)・spec/chip-capabilities.json・tests/・会話記録
   git blameで最初の取り込み88c5da3(2026-06-25)に行き着いた行は、一括の取り込みで個々の理由が無い。その場合は会話記録を探す
3. チップファミリー間の不一致。同種の処理が、チップによって違う作りになっているもの
4. 使われていないコードと、古いままの重複

既知の未対応はdocs/STATUS.mdの「4. 既知の未対応・将来課題」にある。重なるものは、重なることを書いたうえで挙げてよい。
ほかの区切りで見つかった指摘はdocs/plans/code-review-findings.mdにある。この区切りのコードにかかる既出の指摘(<番号>)は親が確かめるので、重ねて調べなくてよい。それらに関係する新しい事実を見つけたら書いてください。

一件ごとに次を書く:
- 種類(1〜4)
- 今のコードのファイル:行。旧実装に対応があれば、そのファイル:行も。行番号は、そのファイルを開いて見た番号を書く
- 何が起きるか、何が違うか
- 2のとき: 根拠の強さと、根拠のある場所。探して見つからなかった場所も書く
- 確度: 確認済み(コードを追って確かめた) / 推測(根拠を一行)

会話記録の原文は引用せず、要旨と発言の番号だけを書いてください。
「使われていない」と書くときは、呼び出し元をリポジトリ全体(core・gui・apps・backends・tests)でgrepして数えた結果を添えてください。
見つかった数は、在る数ではありません。読み切れなかった範囲があれば、最後にその範囲を書いてください。
```
