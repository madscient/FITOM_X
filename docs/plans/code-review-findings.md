# 指摘: コード全体のレビュー(legacyを基準に、2026年11月)

コード全体のレビューで見つかった指摘の一覧。レビューの進め方は`docs/plans/code-review.md`にあり、そちらはレビューが終わったら消す。この文書は残り、指摘を直す作業の計画になる。
直すかどうかは、ユーザーが一件ずつ決めて「判断」の欄に書く。直した項目をこの文書でどう扱うか(消すか、印を付けて残すか)は、最初に直すときに決める。

確度の印: **確認済み** = 走らせて確かめた(何でどう確かめたかを添える) / **未検証** = 作ったが確かめていない / **推測** = 出典を示せない(根拠を一行添える)

## 読み方

- **番号**: 「区切り-連番」。区切りは、1 MIDIの受け口とチャンネル、2 設定とバンク、3 FMのドライバ、4 PSG・PCMのドライバ、5 共通部と契約、6 GUIのブリッジとアプリ
- **行番号**: 各区切りの見出しに書いたHEADのもの。コードを直すと行がずれるので、直す前に開いて確かめる
- **種類**:
  1. **不具合**: 具体的な入力・状態と、誤った結果を書けるもの
  2. **legacyとの違い**: 挙動の違い(書くレジスタと値、MIDIメッセージへの反応、データの解釈、音の高さ・大きさ・時機)。名前・構造・書き方の違いは、挙動を変えない限り数えない
  3. **チップファミリー間の不一致**: 同種の処理が、チップによって違う作りになっているもの(`CLAUDE.md`の必須要件)
  4. **使われていないコードと、古いままの重複**
  5. **決めた仕様との食い違い**: 作り直しのときに決めた仕様と違うのに、コードと文書の辻褄は合っているもの。コードだけでは見えない
- **根拠の強さ**(種類2に付ける。`legacy/src/`を挙動の基準として、違いの根拠がどれだけあるか):
  - **指示**: ユーザー(legacyの設計者)が、作り直しのときに変えるよう指示した
  - **強**: ハードウェアの資料・測定・テストで裏づけられる。またはlegacyの不具合を直したものとして示せる
  - **弱**: 文書・worklog・コミットのメッセージ・会話記録に理由が書かれているが、裏づけは無い
  - **無**: 見つからない。「疑わしい」として扱う
- 括弧の中の`X01-B055`のような番号は、作り直しのときの会話記録の発言の番号(Bはユーザー、Kはアシスタント)。記録はリポジトリの外にあり、記録のあるマシンでだけ引ける。場所と引き方は、そのマシンのClaude Codeのプロジェクトのメモリにある
- **判断**: ユーザーが一件ずつ決めた結果。「未」はまだ決めていない

書式。区切りごとに見出しを作り、一件を1項目で書く。区切りの最後に、legacyとの違いの数を強さごとに書く(指示/強/弱/無)。レビューの後で、legacyの位置づけ(`legacy/README.md`)を決める材料にする。

```text
- **<区切り>-<連番>** <種類> / `<今のコードのファイル:行>`(legacy `<ファイル:行>`) — 何が起きるか・何が違うか。根拠: 強さと場所(探した場所)。確度: 確認済み(何で確かめたか)。判断: 未
```
